# CloudShield Taskboard — Cloud & Cybersecurity Coursework

A small, functional Flask website for a fictional team. It demonstrates cloud deployment, role-based access control (RBAC), password hashing, encryption at rest, CSRF protection, login rate limiting, and HTTP security headers.

## 1. Requirements
- Python 3.10+
- pip

## 2. Run locally (Windows PowerShell)
```powershell
cd cloud_security_project
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
$env:APP_SECRET_KEY = (py -c "import secrets; print(secrets.token_urlsafe(48))")
$env:FERNET_KEY = (py -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")
$env:COOKIE_SECURE = "0"
py app.py
```
Then open http://127.0.0.1:5000/setup and create the first admin. If PowerShell blocks activation, run `Set-ExecutionPolicy -Scope Process Bypass` in that terminal, or use the equivalent commands for your shell.

## 3. Create the fictional team
Sign in as the administrator, open **Team & roles**, and create accounts such as:
- `leyla.security` — Security: reviews security tasks and updates task status
- `murad.engineer` — Engineer: creates and updates implementation tasks
- `nigar.hr` — HR: read-only project visibility and team-role overview
- `samir.viewer` — Viewer: read-only dashboard access

Use unique temporary passwords of at least 12 characters. The site does not create default users or ship with default passwords.

## 4. Deploy publicly on Render
1. Create a Git repository and upload the project files. Do **not** upload `.env`, `app.db`, or secrets.
2. In Render, create a new Blueprint/Web Service from that repository; `render.yaml` provides the service configuration.
3. Set `FERNET_KEY` as a secret environment variable. Generate it locally with:
   ```bash
   python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```
   Keep the same key permanently. If it changes or is lost, previously encrypted task details cannot be decrypted.
4. `APP_SECRET_KEY` is generated by Render in the blueprint. Confirm `COOKIE_SECURE=1`.
5. The blueprint mounts a persistent disk at `/var/data` for SQLite. Confirm the selected Render plan supports persistent disks and review its cost/availability. For a larger real deployment, use managed PostgreSQL and a managed secret store.
6. Deploy, open the public URL, and visit `/setup` once to create the first administrator.
7. Test login, roles, CSRF-protected forms, and task creation. Make sure the service is served over HTTPS.

**Important:** A web app is only as safe as its deployment and maintenance. Do not put real sensitive data in this student demo. Set backups, access controls and monitoring before any real use.

## 5. Security design
- Passwords: Werkzeug password hashing (currently uses its secure default PBKDF2-based implementation), never plaintext storage.
- Encryption: task details encrypted with Fernet (AES-based authenticated encryption). The key is external to the database.
- RBAC: authorization checks run on the server for user administration and task create/update endpoints.
- CSRF: Flask-WTF validates state-changing form submissions.
- Rate limiting: login and first-run setup have limits; application also has default per-IP limits.
- Headers: CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy and HSTS on HTTPS requests.
- Session cookies: HttpOnly, SameSite=Lax; Secure is enabled for cloud deployment through `COOKIE_SECURE=1`.
- Input constraints: form validators, title/description length limits, 1 MB request limit, SQL parameter binding and Jinja auto-escaping.
- No default user/password; first-run setup closes once the first user exists.

## 6. Known limitations
This is a coursework starter, not a professional security product. Before real-world use: add automated tests, audit logging, password reset and MFA, account lockout / anomaly detection, dependency scanning, robust secret rotation, database backups, a managed database, security monitoring, and a reviewed production configuration. SQLite is intended for a small demonstration only. The generated temporary Fernet fallback is for local development and is not suitable for persisted data; always set `FERNET_KEY` in production.
